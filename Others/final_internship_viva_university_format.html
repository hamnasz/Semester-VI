    Project 1 · Weeks 6–7

    Problem & objective

    THE PROBLEM

    Pakistani users routinely mix Roman Urdu and English within the same sentence — sometimes the same phrase. Most NLP tools assume a document is written in a single language, so this code-switched text is hard for them to process correctly.

    THE OBJECTIVE

    Build a model that reads a sentence and labels every word as one of three classes — a word-level token classification problem, not a sentence-level one.

    URDENGMIX
    [1] example sentence
    mujhe office se late reply mila # URD ENG URD URD ENG URD

    Real-world uses: sentiment analysis on mixed-language text, keyboard suggestions and chatbots that don't break on Roman Urdu, and content-moderation systems that currently assume a single language.

    Why a plain wordlist wasn't enough

    Common Urdu words like is, mil, beta, par are also valid English words. A curated override list of 150+ common Urdu words caught these before the English wordlist could misclassify them. A case-insensitive de-dupe pass also fixed a bug where the same sentence was kept twice under different capitalisation.

    Urdu OCR · The Failure That Taught Me the Most

    The model failed. The debugging succeeded.

    0%
    exact-match accuracy, 52 held-out images
    ~0.1%
    mean character-level similarity

    Every prediction collapsed to the same fixed 20-character placeholder string, no matter what the input image contained.

    INVESTIGATION 01
    Predictions were checked side by side — every single one was identical, regardless of the input image.
    INVESTIGATION 02
    Training data was checked next: row counts in labels.csv compared against image files that actually loaded.
    INVESTIGATION 03
    153 of 263 rows (58%) were being silently skipped during training — no error, no warning.
    ROOT CAUSE
    labels.csv had picked up two incompatible file-path conventions from different weeks of data collection. The loader only handled one of them.
    FIX
    Wrote resolve_image_path() — tries the direct path first, falls back to the older convention. Restored the dataset to its full 263 rows.
    Figure 10 · Evaluation on the held-out test set — the collapse pattern.
    Figure 11 · Sample predictions against ground truth.

    Most likely causes, traced (not guessed)

    • The base model's decoder is a RoBERTa model pretrained almost entirely on English — very little Urdu representation to start from.
    • A domain gap between scanned / photographed / synthetic dataset images and the base model's original printed-text pretraining data.
    • Only 211 training examples across 3 epochs — a small amount of signal to teach an entirely new writing system.
    • The repeated-character pattern is consistent with exposure bias, a known failure mode in sequence-generation models.

    💬 General

    What did you learn during the internship?
    The full applied ML lifecycle: framing a problem, building a dataset, fine-tuning transformer models, evaluating honestly, debugging failures, and deploying to Streamlit + the Hugging Face Hub — plus how to manage a multi-week project independently.
    What was your biggest challenge?
    The Urdu OCR model collapsing to a single repeated output with 0% exact-match accuracy — and having to diagnose why with no instructor checking each step in real time.
    Which project was more difficult, and why?
    Urdu OCR — it ran 5 weeks instead of 2, needed a dataset built almost from scratch (263 pairs), and the low-resource script gave the base model very little to start from.
    What technologies did you use?
    Python, PyTorch, Hugging Face Transformers (XLM-RoBERTa, TrOCR), pandas/NumPy, OpenCV/Pillow, Tesseract, Matplotlib/Seaborn/scikit-learn, Git/GitHub, Hugging Face Hub, and Streamlit.

    🔤 Code-Switching

    Why is code-switching difficult for NLP tools?
    Most NLP tools assume one language per document. Roman Urdu–English text mixes languages within a sentence or phrase, so word-level, not sentence-level, handling is needed.
    Why did you use XLM-RoBERTa?
    It's a multilingual transformer, well suited to a token-classification setup across Urdu and English tokens in the same sentence.
    What is token classification?
    Labelling each individual token (word) in a sequence, rather than the sequence as a whole — here, tagging every word URD, ENG, or MIX.
    Why did MIX score an F1 of 0?
    The auto-labelling step only accepted strictly alphabetic tokens, so hyphenated hybrid words — the natural form of MIX tokens — were filtered out of the training data before they could ever be labelled MIX. The model correctly learned that MIX almost never occurs, because in its training data it never did.
    How did you build the dataset?
    Cleaned ~15,900 sentences from a public Roman Urdu dataset, auto-labelled with an English wordlist plus a 150+ word Urdu override list, filtered to 220 genuinely code-switched sentences, then manually spot-checked (~95% estimated correctness) to reach 2,490 word-level labels.
    How did you evaluate the model?
    An 80/20 held-out split, reporting precision/recall/F1 per label plus a confusion matrix — not just overall accuracy, so the MIX failure was visible rather than averaged away.

    🖼️ OCR

    Why is Urdu OCR difficult?
    Urdu's Nastaliq script is highly cursive, flows diagonally, and each letter changes shape by position — and there's far less labelled Urdu OCR data available than for English.
    Why did you use TrOCR?
    It's a transformer encoder-decoder built for image-to-text generation, so it was a reasonable starting point to fine-tune for a new script rather than building an OCR architecture from scratch.
    Why did Tesseract perform poorly?
    It's a general-purpose OCR engine not tuned to this dataset's mix of scanned, photographed, and synthetic Urdu text. It recovered only 27% and 0% of words on the two images with exact ground truth, and hallucinated characters not present in the source.
    What caused the OCR model to fail?
    Three traced factors: the decoder's pretraining is almost entirely English, so it had little Urdu representation; a domain gap between the dataset's images and the base model's original pretraining data; and only 211 training examples across 3 epochs — too little signal for a new writing system. The pattern matches exposure bias, a known sequence-generation failure mode.
    What was the 153/263 dataset bug?
    labels.csv had picked up two incompatible file-path conventions from different weeks of data collection. The loader only handled one, so 153 of 263 rows (58%) were silently skipped during training with no error or warning.
    How did you fix it?
    Wrote resolve_image_path(), which tries the direct path first and falls back to the older convention — restoring the dataset to its full 263 rows. Found only because I'd started comparing row counts against loaded-file counts as a habit.
    What would you do differently next time?
    Plan for a longer, more iterative training process from the start on a low-resource script rather than treating one 3-epoch run as final, and add a dedicated pipeline-correctness checkpoint earlier — checking label distributions and file-path consistency before it reaches model evaluation.

    🛠️ Engineering

    Why use the Hugging Face Hub?
    It hosts both the fine-tuned weights and the dataset in one place, and the deployed Streamlit apps load the model directly from the Hub — no manual file handling for a user trying the app.
    Why use Streamlit?
    It let me turn a notebook result into something another person could actually open and use — type a sentence or upload an image and see the output — with a small amount of code.
    What role did Git/GitHub play?
    Both projects were kept under version control throughout, not written up after the fact — 221 commits on the OCR repo, 30 on the code-switching repo — so the commit history is itself a record of the iterative, trial-and-error process.
    What did you learn from debugging?
    That most of the costly bugs (the MIX label loss, the 153/263 file-path bug) were data problems, not model problems — and that habits like comparing row counts or checking label balance catch them far earlier than waiting for a bad evaluation number.
